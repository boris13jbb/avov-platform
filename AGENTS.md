## Learned User Preferences

- Comunicar y documentar el proyecto en español.
- Commit, push, pull request, merge y despliegue son acciones independientes: cada una exige su propia autorización explícita, y autorizar una no autoriza la siguiente. Un fallo de CI permite investigar y preparar una corrección, pero no autoriza commit, push, merge ni despliegue. Conservar los cambios locales ajenos a la tarea.
- No ejecutar Git destructivo, `docker compose down -v`, borrado de volúmenes, ni detener XAMPP o contenedores de otros proyectos sin una autorización nueva.
- Antes de cambiar puertos, autenticación, esquema o infraestructura, presentar la propuesta y esperar autorización, salvo que esa acción concreta ya esté autorizada. Evaluar o explicar un riesgo no autoriza a ejecutar el cambio. No rotar la contraseña del superadministrador, no ejecutar el bootstrap del administrador contra `avov_db` y no modificar la migración histórica `e1f2a3b4c5d6_seed_super_admin.py` sin una autorización nueva.
- Las reglas del repositorio fijan arquitectura, stack, convenciones y entorno de prueba; una regla global genérica no las sustituye. AVOV usa Riverpod y GoRouter. No imponer Provider, ChangeNotifier ni Firebase salvo que el repositorio ya los use. Las instrucciones explícitas del usuario fijan el alcance de cada tarea. Si chocan en datos, historial o alcance aprobado, detenerse y preguntar. No trasladar fases, puertos ni restricciones de este proyecto a otros.
- No afirmar que una prueba, una regla de Cursor o una tarea quedó hecha si no se comprobó. Un E2E manual no se aprueba solo porque pasen tests automatizados o porque la URL responda HTTP 200; el health HTTP 200 tampoco prueba por sí solo el aislamiento de esquema de base de datos. En E2E hay que distinguir observación de UI frente a verificación HTTP: reportar «healthy» o HTTP 200 en Flutter Web no implica que la UI esté montada. El navegador IDE de Cursor a menudo no renderiza el canvas de Flutter Web (negro o sin a11y útil); preferir Chrome lanzado por Flutter para observar la UI. Abrir `:3001` a mano en un Chrome cualquiera (sin el Chrome hijo del `dartvm` de ese `flutter run`) suele dejar pantalla blanca aunque el puerto responda 200. En el Chrome E2E acoplado, mantener el origen `http://localhost:3001` y no cambiar el host a `127.0.0.1` (ni al revés): ese cambio correlaciona con pantalla blanca y remount DDC. Si el operador ya autenticó la sesión QA, no cerrar sesión, no recargar ni forzar cambio de host. Los clics sintéticos de computer-use sobre `OutlinedButton` de Flutter Web son poco fiables; puede hacer falta un clic físico, y un fallo del clic sintético no se trata como defecto del producto. En Windows, enviar hot restart (`R`) a la consola Flutter vía `AttachConsole`/`WriteConsoleInput` contra ConPTY suele fallar con WinError 6; no improvisar métodos alternativos ni reinicios completos sin autorización explícita, y al operar en E2E `:3001` preservar intacta la instancia Flutter principal `:3000`.
- La política de calidad es universal para todos los lenguajes; las guías de React y TypeScript no se aplican a Flutter ni a Python/FastAPI. Esas reglas deben seguir disponibles en otras computadoras, en el repositorio y en la configuración de usuario de Cursor.
- No mostrar secretos, contraseñas, tokens, hashes reales ni el contenido de `.env`. No inventar credenciales ni afirmar que existen cuentas de prueba no verificadas en el entorno o en la documentación. En E2E, las credenciales QA viven fuera del repo en `%LOCALAPPDATA%\AVOV\e2e\qa-student.json` (abrir con `Win+R` → `%LOCALAPPDATA%\AVOV\e2e`); se introducen solo en el formulario del navegador y no se pegan en el chat, informes, capturas, logs ni documentación. Las credenciales de `:3000`/`avov_db` no sirven contra `:8001`/`avov_test`.
- Trabajar de forma incremental sobre la copia abierta: no reclonar el proyecto ni reinstalar herramientas que ya están configuradas.

## Learned Workspace Facts

- Repositorio oficial: `https://github.com/boris13jbb/avov-platform.git`. La copia abierta en Cursor es `C:\Users\BRS\Documents\AVOV`. También existe un clon en `C:\Users\BRS\source\avov-platform`; no sobrescribir copias existentes.
- El trabajo de continuidad en Windows está en la rama `docs/windows-continuity`, no directamente en `main`.
- En este equipo, XAMPP (`mysqld`) ocupa el puerto 3306 y debe permanecer intacto. MySQL de AVOV (imagen 8.4, contenedor `avov-mysql`, base `avov_db`) se publica como `3307:3306`; dentro de Docker el backend usa `mysql:3306`. phpMyAdmin se publica en el puerto 8081. Adminer en el puerto 8080 no es la base de AVOV.
- El puerto 6379 del host lo usa el contenedor ajeno `sc-pne-redis`. Redis de AVOV se publica como `6380:6379`; dentro de Docker la URL es `redis://redis:6379/0` y el valor local por defecto en Windows es `redis://127.0.0.1:6380/0`. No conectar AVOV a las redes de `sc-pne-*` ni de `fortaleza-*`.
- La API activa local se comprueba en `http://127.0.0.1:8000/api/v1/health` (Redis DB `0`). Qdrant de AVOV se publica en `:6333`. Flutter Web de desarrollo suele servirse en el puerto 3000; un proceso Flutter antiguo ahí puede mostrar UI desactualizada — hay que detenerlo y relanzar desde `frontend/`. El E2E aislado usa API `127.0.0.1:8001` (Redis DB `1`, esquema `avov_test`) y Flutter Web en `3001` con `--dart-define=API_BASE_URL=http://127.0.0.1:8001/api/v1`, vía `scripts/dev-backend-e2e-isolated.ps1`, `stop-backend-e2e-isolated.ps1`, `verify-backend-e2e-isolated.ps1` y `dev-frontend-e2e-isolated.ps1`, sin tocar `:8000`/`:3000`. El PID de `Start-Process` del backend E2E es el padre; el listener de `:8001` suele ser un hijo. Un abort/`exit_code: 1` del wrapper o harness no implica que uvicorn haya caído; comprobar health y `verify-backend-e2e-isolated.ps1`. Son entornos distintos: principal `:3000`/`:8000`/`avov_db` frente a E2E `:3001`/`:8001`/`avov_test`; la UI E2E requiere el Chrome lanzado por ese `flutter run` (hijo del `dartvm` de `:3001`) en origen `http://localhost:3001`, no solo abrir la URL en otro navegador ni cambiar el host a `127.0.0.1`. Al pedir detener puertos o levantar AVOV, actuar solo sobre servicios `avov-*` y puertos de AVOV; no tocar XAMPP ni contenedores `sc-pne-*`, `fortaleza-*` o `gim-pro-*`.
- Las pruebas de backend que escriben datos deben usar la base aislada `avov_test`, no `avov_db`. La guardia fail-fast está en `backend/tests/db_isolation.py` y se ejecuta en `pytest_configure` de `backend/tests/conftest.py`: solo el schema `avov_test` está autorizado; la validación corre antes de imports de test que crean el engine; no hay bypass por excepción de módulo. Demostrar el schema con env del proceso, processlist de MySQL o preflight, no solo con health 200. En `avov_db` ya se aplicaron las migraciones de Alembic hasta `f4b5c6d7e8f9`.
- Los tokens de Flutter se guardan con `frontend/lib/core/storage/secure_token_storage.dart` mediante almacenamiento seguro. Ante HTTP 401, `AuthInterceptor` llama a `POST /auth/refresh` con `{ "refresh_token" }` (rotación de tokens) antes de limpiar la sesión. Las contraseñas se hashean con Passlib 1.7.4 y bcrypt 4.2.1 en formato `$2b$`. Un hash desconocido se trata como autenticación fallida, sin exponer el detalle.
- En producción la aplicación no arranca con `APP_DEBUG` activo ni con marcadores exactos de ejemplo en secretos JWT, de aplicación o de base de datos, ni con la clave de DeepSeek de ejemplo. El error nombra la variable y no imprime el valor.
- El límite de intentos de login reserva el cupo en un script atómico de Redis y responde 429 sin comprobar la contraseña. Si el proxy es de confianza, se usa el último valor de `X-Forwarded-For`. El bootstrap del administrador no corre al arrancar ni desde migraciones, y no cambia el hash de una cuenta ya existente. La cuenta instalada en `avov_db` y la migración histórica de semilla quedan pendientes de una autorización aparte.
- Las reglas de calidad del repo están en `.cursor/rules/`; hay copia de usuario en `%USERPROFILE%\.cursor\rules\`. `react-typescript-calidad.mdc` solo aplica a archivos TypeScript o TSX de React. La política de Git activa en archivos es `C:\Users\BRS\.cursor\rules\git-github-workflow-policy.mdc`; `git-github-workflow-policy.USER-RULES.txt` es una copia auxiliar y no es una User Rule activa. Las User Rules de Cursor Settings tituladas `creating-pull-requests` y `Global Rules File — Flutter Enterprise Agent` viven en la base de conocimiento de la cuenta, no en `settings.json` ni en archivos de `.cursor/rules`. El agente no puede editarlas; hay que sustituirlas a mano en Cursor Settings.
- En Flutter, el destino tras el login depende del rol: `SUPER_ADMIN` usa el panel de administración; `INSTITUTION_ADMIN` entra al panel de su institución y gestiona estudiantes y orientadores; `COUNSELOR` entra al panel del orientador y solo consulta estudiantes asignados en `counselor_assignments`; `STUDENT` entra en `/student/dashboard` con menú (drawer/rail) a Inicio, Test, Resultados y Perfil. El estudiante es un perfil de `/students` con usuario anidado; el propio estudiante usa `GET /students/me`. Un orientador es un usuario `COUNSELOR` en `/users`. `GET /students` sigue cerrado para `STUDENT` y no hay endpoint para asignar estudiantes a un orientador. Para E2E del espacio estudiante hay que confirmar que el rol real es `STUDENT` (p. ej. vía `/auth/me`); una cuenta etiquetada como de prueba puede ser `INSTITUTION_ADMIN` y provocará 403 en rutas de estudiante.
- El test del estudiante usa el contrato real del backend: `GET /tests` lista el historial; `POST /tests/start` reutiliza una sesión `STARTED` o `IN_PROGRESS` y responde 422 si hay varias abiertas; las preguntas se ordenan por `order_number`; cada respuesta va con `POST /tests/{id}/answers` en escala 1–5; el cierre es `POST /tests/{id}/finish`. En Flutter, con varias abiertas se elige desde el historial o el lanzador sin llamar a `start` a ciegas; «Continuar esta evaluación» navega a la sesión por `ValueKey` (`continue-open-{id}`, `dash-continue-{id}`), visibles en el inspector Flutter pero no en DOM/AX ni como ID en la etiqueta. En la rama S-21 (`feature/s21-career-recommendations`) el router de recomendaciones está montado (`GET`/`POST /recommendations/sessions/{id}`); la UI muestra carreras en el resultado y, si la lista persistida está vacía, el provider puede llamar a `generate` (no abrir sesiones de evidencia 137–139 si se quiere evitar escribir `recommendations`). El backend expone `POST /auth/change-password`; en Flutter no hay pantalla ni `GoRoute` de cambio de contraseña (se eliminó la constante huérfana). La cuenta `STUDENT` de E2E aislado se prepara con `backend/scripts/create_e2e_student_qa.py`; las credenciales viven en `%LOCALAPPDATA%\AVOV\e2e\qa-student.json` (nunca en chat, docs ni git). Con JWT compartido entre APIs, las identidades QA en `avov_test` usan IDs altos (≥900000) para que `:8000` las rechace (401) si el token cruza. El registro append-only de evidencias E2E del espacio estudiante está en `docs/s-20-e2e-estudiante.md`.
