## Learned User Preferences

- Comunicar y documentar el proyecto en español.
- Commit, push, pull request, merge y despliegue son acciones independientes: cada una exige su propia autorización explícita, y autorizar una no autoriza la siguiente. Un fallo de CI permite investigar y preparar una corrección, pero no autoriza commit, push, merge ni despliegue. Conservar los cambios locales ajenos a la tarea.
- No ejecutar Git destructivo, `docker compose down -v`, borrado de volúmenes, ni detener XAMPP o contenedores de otros proyectos sin una autorización nueva.
- Antes de cambiar puertos, autenticación, esquema o infraestructura, presentar la propuesta y esperar autorización, salvo que esa acción concreta ya esté autorizada. Evaluar o explicar un riesgo no autoriza a ejecutar el cambio. No rotar la contraseña del superadministrador, no ejecutar el bootstrap del administrador contra `avov_db` y no modificar la migración histórica `e1f2a3b4c5d6_seed_super_admin.py` sin una autorización nueva.
- Las reglas del repositorio fijan arquitectura, stack, convenciones y entorno de prueba; una regla global genérica no las sustituye. AVOV usa Riverpod y GoRouter. No imponer Provider, ChangeNotifier ni Firebase salvo que el repositorio ya los use. Las instrucciones explícitas del usuario fijan el alcance de cada tarea. Si chocan en datos, historial o alcance aprobado, detenerse y preguntar. No trasladar fases, puertos ni restricciones de este proyecto a otros.
- No afirmar que una prueba, una regla de Cursor o una tarea quedó hecha si no se comprobó.
- La política de calidad es universal para todos los lenguajes; las guías de React y TypeScript no se aplican a Flutter ni a Python/FastAPI. Esas reglas deben seguir disponibles en otras computadoras, en el repositorio y en la configuración de usuario de Cursor.
- No mostrar secretos, contraseñas, tokens, hashes reales ni el contenido de `.env`.
- Trabajar de forma incremental sobre la copia abierta: no reclonar el proyecto ni reinstalar herramientas que ya están configuradas.

El bootstrap del administrador no corre al arrancar ni desde migraciones, y no cambia el hash de una cuenta ya existente. La cuenta instalada en `avov_db` y la migración histórica de semilla quedan pendientes de una autorización aparte.
- Las reglas de calidad del repo están en `.cursor/rules/`; hay copia de usuario en `%USERPROFILE%\.cursor\rules\`. `react-typescript-calidad.mdc` solo aplica a archivos TypeScript o TSX de React. La política de Git activa en archivos es `C:\Users\BRS\.cursor\rules\git-github-workflow-policy.mdc`; `git-github-workflow-policy.USER-RULES.txt` es una copia auxiliar y no es una User Rule activa. Las User Rules de Cursor Settings tituladas `creating-pull-requests` y `Global Rules File — Flutter Enterprise Agent` viven en la base de conocimiento de la cuenta, no en `settings.json` ni en archivos de `.cursor/rules`. - En Flutter, el destino tras el login depende del rol: `SUPER_ADMIN` usa el panel de administración; `INSTITUTION_ADMIN` entra al panel de su institución y gestiona estudiantes y orientadores; `COUNSELOR` entra al panel del orientador y solo consulta estudiantes asignados en `counselor_assignments`; `STUDENT` entra en `/student/dashboard`. El estudiante es un perfil de `/students` con usuario anidado. Un orientador es un usuario `COUNSELOR` en `/users`. No existe `GET /students/me`, `GET /students` está cerrado para `STUDENT` y no hay endpoint para asignar estudiantes a un orientador.

No hay historial de sesiones ni recomendaciones de carreras.
